## SDK contract checked

Installed lockfile dependency is `@google/genai@2.10.0`. Its declarations support `ai.models.generateContent({ model, contents, config })`, JSON response MIME type, `responseJsonSchema`, and `abortSignal`. The existing call uses the correct method family, but discards most request config fields and times out with `Promise.race` without aborting the SDK request. SDK retry-after/header behavior and a real model response remain unverified without credentials.

## ML capability classification

| Capability | Current classification | Evidence / limitation |
|---|---|---|
| Task completion probability | `DETERMINISTIC_HEURISTIC` | Weighted sigmoid; no fit model, learned artifact, or real outcome data. |
| Task duration estimation | `NOT_IMPLEMENTED` | Uses user-entered estimated minutes/hours as input. |
| Deadline risk | `DETERMINISTIC_HEURISTIC` | Thresholds the heuristic completion probability. |
| Workload/capacity pressure | `DETERMINISTIC_HEURISTIC` | Deterministic availability and scheduling calculations. |
| Focus-window suitability | `DETERMINISTIC_HEURISTIC` | Deterministic scoring over feasible windows and profile preferences. |

No valid historical user-outcome dataset or trained model artifact is present. Synthetic generator labels are created from simple rules and are not evidence of predictive performance on users. A useful first honest release is therefore a typed heuristic interface with explicit source and data-sufficiency metadata; fitting a trained model is blocked on valid labeled history and a leakage-controlled evaluation split.

## Repair status and verification

The confirmed implementation defects above were repaired in this working tree:

- Root `.env` is loaded on the server before the shared Gemini router singleton initializes. Only `GEMINI_API_KEY` is read server-side; placeholder keys are treated as missing.
- The router uses the installed `@google/genai` 2.10.0 API, passes the structured JSON schema and system instruction, aborts timed-out requests, disables hidden SDK retries so the router owns bounded attempts, validates model IDs, and supports only explicitly configured fallbacks. Provider failures return sanitized categories and raw provider exceptions are not logged.
- Reasoning outputs are parsed as strict JSON objects and validated against operation-specific fields, bounds, and trusted indices. LLMs only refine explanations and cannot set numerical confidence or authorize actions.
- `/api/chat` now accepts only the message from the client and routes through authenticated, server-built context. Unsupported or unavailable intelligence returns a degraded/error result instead of fabricated success text.
- Python training now fails closed without validated labeled history. Prediction and UI surfaces label the existing capability as heuristic or unavailable, and no longer display simulated training metrics as model accuracy.

### Confirmed real-data model and integration

- Target trained: `task_completion_lead_time = (Resolved - Created)` in elapsed calendar days. It does not estimate active working time, focused work, completion probability, or deadline risk.
- All 1,193 records had `Done` status, valid nonblank summaries, parseable creation and resolution timestamps, and positive lead time. No full-row duplicates were found. Six rows with repeated normalized Summary titles were excluded because no stable task identifier exists. Usable count: 1,187.
- Features: title `Summary` only. Text preprocessing fits TF-IDF on the training data; Ridge regression is trained against `log1p` target. Status and Resolved are post-outcome; Created is used only for target/split; Priority, Labels, and Description lack point-in-time provenance and are excluded.
- Split: chronological train/validation/test = 830/178/179; model selection on validation chose Ridge alpha 100; final fitting used 1,008 train-plus-validation rows.
- Held-out test metrics (N=179): median baseline MAE 620.980 days, RMSE 621.109 days, median absolute error 621.168 days, R² -2413.171; TF-IDF+Ridge MAE 281.799 days, RMSE 282.299 days, median absolute error 282.523 days, R² -497.712. MAE is lower than the baseline on this split, but the strongly negative R² and the source selection bias indicate poor general reliability. This is not calibrated or production-validated.
- Artifact: ignored `ml/models/task-lead-time-v1.joblib`; manifest in the same ignored directory; tracked measured report `ml/reports/task-lead-time-v1.json`. The manifest records source/file checksum, feature schema, target, split, dependencies, metrics, limitations, and artifact hash. Loader validates these contracts and checksum before load.
- Runtime: one persistent JSON-lines Python worker is used by `TaskLeadTimePredictionService`; it loads the artifact once and returns explicit `unavailable` status instead of substituting a heuristic. `PrioritizerAgent` requests predictions only for tasks explicitly tagged `software-engineering`, `software engineering`, or `jira`, and exposes them as advisory metadata. It does not change task ranking or authorize execution; existing proposal confirmation remains in force.
- Prioritizer integration was exercised with a real held-out workbook title. Test asserts trained-model provenance, elapsed-day units, finite output, and confirmation-required actions. No title is printed by the test.
- The former synthetic-label diagnostic remains named `synthetic_diagnostic_only`, is preserved for legacy checks, and is not used as model evidence or quoted as real performance.

## ML reliability diagnosis and runtime restriction (2026-10-19)

The saved `task-lead-time-v1` artifact and evaluation were reproduced using the root workbook. Split sizes are 830/178/179 (train/validation/test). Final model held-out test MAE/RMSE/R² are 281.799 days / 282.299 days / -497.712. The matching train-plus-validation median baseline is 620.980 / 621.109 / -2413.171; the mean baseline is 591.553 / 591.688 / -2189.879. Lower MAE than those shifted baselines is not evidence of a useful model.

Test target standard deviation is 12.641 days and mean 15.145 days, but the model predicts mean 296.943 days (range 256.954–326.935); mean residual is +281.799 days. Test target maximum is 58.965 days, whereas train median is 761.692 days and train maximum is 3,367.934. Nine train rows exceed train p99 (1,151.485 days), but no validation/test row does. The distributions indicate severe chronological regime shift. Data is restricted to completed Jira issues, has no task ID or summary revision history, and uses title text only. R² is strongly negative because squared error is enormous relative to the low variance in the held-out slice. Full per-split metrics and diagnostics are in `ml/reports/task-lead-time-v1-diagnostics.json`; reproduce with `python -m ml.evaluation.diagnose_task_lead_time`.

`TaskLeadTimePredictionService` returns `status=unavailable`, `source=unavailable`, `reason=experimental_model_disabled` by default. The artifact and persistent-worker integration remain guarded behind the explicit experimental flag but are not enabled by the application or its tests. Missing/corrupt artifacts still return unavailable; no heuristic is represented as model output. The current PrioritizerAgent integration test asserts default-disabled behavior, empty predictions, unchanged deterministic ranking, and confirmation-required proposals.

## Opt-in task outcome instrumentation (2026-10-19)

The task persistence audit found only mutable task state, not an outcome-training event log. Tasks store creation time, priority, local due date/time, `estimatedMinutes`, status and `completedAt`; the 30-minute default estimate is indistinguishable in the task row from a user-supplied estimate. Completion timestamps represent a Nova status transition, not verified active work. Goals/projects have mutable status/progress and `updatedAt` but no dedicated immutable completion timestamp. Decision telemetry captures acceptance/execution workflow outcomes but does not preserve prediction-time feature snapshots. No historical values were backfilled.

Added explicit per-user opt-in and a minimal `schemaVersion:1` task-outcome record in `data/task_ml_outcomes.json` (existing local JSON storage architecture). Settings exposes the authenticated consent control; opt-in is false by default, and opt-out disables capture before clearing records. New task snapshots are collected only after consent, with no titles/descriptions/tags. Feature fields retain value, provenance (`user_entered`, `imported`, `system_observed`, `derived`, `unknown`), and an observed/missing bit. Explicitly supplied task estimates are distinguished from the task store's default. Category remains unavailable because Nova's task schema has no category field. A completion event is recorded only when an earlier opt-in snapshot exists; duplicate event capture is idempotent, deletion removes its record, and tenant reads use the authenticated user partition. Deadline outcome remains null when the captured due date/timezone cannot support a defensible label. Collection never influences prioritization or enables the experimental Jira model.

Validation checks timestamps/order, field and provenance schema, enums and bounds, no unexpected fields, completion-before-snapshot errors, and missing-value representation. Tests cover tenant isolation, opt-in gating, immutable feature snapshots, completion target construction, deadline labels, missing estimates/deadlines, duplicate snapshots/completions, invalid timestamps, and rejecting injected title fields. The exact schema and limitations, plus a future minimum-data/evaluation plan, are in `docs/ML_DATASET_METHOD.md`.

### Consent and outcome-capture HTTP hardening

Added `npm run test:ml:outcomes:http`, which starts the actual Express server under a temporary working directory and exercises its authenticated consent and task APIs through the existing `requireAuth` middleware. It covers unauthenticated rejection, default-off consent, user isolation, malformed/extra/schema-version request fields, future-only snapshots, pre-consent completion, explicit estimates and timezone snapshots, data-minimized storage, repeated completion/reopen behavior, task deletion, opt-out purge, and sanitized error responses. The test-only HMAC sessions are local test fixtures; no auth middleware was copied into application code.

Outcome and profile/consent JSON now use unique same-directory temp files, write-then-rename, and POSIX `0600` file / `0700` data-directory permissions. The files remain excluded from Git. This provides atomic replacement and basic same-host access restriction, **not encryption**. Windows ACLs are inherited and were not verified. The stores remain in-memory cached JSON with no interprocess locking or transactional guarantees; stale multi-process caches can overwrite newer data. Supported deployment for opt-in capture is one server process on one local filesystem under a restricted OS account. Shared/multi-instance deployment needs transactional storage and tested per-user purge semantics first.

Task deletion removes the corresponding record best-effort; opt-out persists disabled consent before user-scoped purge. No account-deletion route/hook currently exists, so account-wide deletion is not automatic and requires a future lifecycle integration or operator cleanup. A task has one completion record only: reopening and completing again keeps the first completion; separate cycles are unsupported. The comparison to local-only storage and retention limitations are documented in `docs/ML_DATASET_METHOD.md`. The specific new integration test and full requested verification commands are recorded below only after this hardening run.
